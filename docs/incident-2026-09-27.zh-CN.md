# Windows SSH 连接故障复盘

发生日期：2026-09-27。整理公开版本：2026-09-29。

本文综合当时已经落盘的早期日志、后续工具验证结果及最终兼容脚本整理。后续一次完整日志写入遇到工具宿主超时，因此早期日志不能代表最终排查结论。公开版本不包含原始会话、真实主机地址、账户名、密钥路径、进程编号或原始客户端命令。

## 环境与目标

目标为 ChatGPT app 经 SSH 连接一台 Windows 主机，使用主机现有 Codex 工作环境。Windows 报告版本为 10.0.22631；默认 SSH shell 是 Git Bash，客户端的 Windows 启动路径调用 Windows PowerShell。连接通过现有 VPN 网络，没有对外开放 app-server 端口。

## 1. 区分连接方向

主机上同时存在通向另一台机器的 SSH 连接。最初看到的活动 SSH 进程属于另一项工作；恢复上一轮记录后，才确认本任务是 **app → 当前 Windows 主机**。诊断首先要确认客户端、服务端、用户名、端口和默认 shell，不能只看某个活跃 ssh 进程。

## 2. SSH 身份与旧 WSL 入口

OpenSSH 事件记录连续出现 `Invalid user`。客户端仍使用停用的 WSL 用户名连接 Windows SSH 端口。改成真实 Windows 用户名后，事件记录变为认证成功。

此前并存 WSL 转发、Windows 常驻任务和手工启动脚本。上一轮已备份并停用旧 WSL 任务、转发和专用防火墙规则；本轮清理残留的 WSL SSH 别名。这里不发布机器专属的删除命令。

**结论：** 认证失败与登录后卡住是两个独立问题。修复用户名后仍要继续检查协议层。

## 3. SSH PATH 与后台版本不一致

本地后台已经运行 Codex 0.157.1，但 SSH shell 的 `codex` 仍解析到全局 npm 安装的 0.153.4。旧版本的 daemon 命令返回不支持 Windows 的错误。

分别检查非交互 shell 和 `bash -l -i`，将 SSH 环境优先指向存在的托管运行时后，两者均返回 0.157.1；后台状态返回 `running`，CLI、托管包和 app-server 版本一致。

官方文档也要求远端登录 shell 能从 PATH 找到 Codex。[OpenAI 远程连接说明](https://learn.chatgpt.com/docs/remote-connections#connect-to-an-ssh-host)

## 4. 后台服务的权限与生命周期

上一轮已发现失效 socket 和控制目录的继承权限问题。新版拒绝从管理员 SSH 会话直接启动共享 daemon，避免共享客户端继承管理员权限。

采用普通用户交互登录计划任务运行后台，SSH 只访问本地代理；任务配置不因切换到电池而停止。没有把管理员启动限制绕开，也没有将 app-server 暴露到公共网络。

此任务依赖用户交互登录。没有验证注销、开机无人登录或重启后的恢复能力。

## 5. 普通协议测试通过，实际 app 启动脚本仍失败

使用 SSH 直接连接 proxy 时，WebSocket、`initialize`、`account/read`、`model/list` 均正常。模拟 POSIX 登录 shell 的测试约 2.6 秒完成。

实际客户端使用的是另一条 Windows PowerShell bootstrap。捕获并在本地测试该命令后，能够看到“就绪”标记，但握手或后续 `initialize` 仍超时。

排除过程：

| 实验 | 结果 |
| --- | --- |
| 给 proxy 关闭 stdin 并等待退出 | 能正常退出，未支持“健康探针一直挂住”的初始猜测 |
| 子进程直接继承 PowerShell 标准句柄 | 该 SSH 路径仍未通过 |
| 双向独立任务，但使用 `Console.OpenStandardInput()` | 可完成握手，后续初始化帧仍停滞 |
| 从 `GetStdHandle(-10)` 创建 `FileStream`，双向传输并 Flush | 初始化、账号状态、模型列表全部通过 |

测试确认 stdin 是重定向管道，不是交互控制台。最后的实现不需要切换控制台模式。

**证据支持的结论：** 这条 PowerShell/SSH 管道路径中，替换输入流读取方式解决了观察到的停滞。没有给 Windows PowerShell 的所有版本、所有 ConsoleStream 使用场景做根因证明；该结论不应扩大为通用平台缺陷。

## 6. 每次重连都覆盖 helper

多次修改后发现，客户端会重新生成控制目录内的旧 `codex-proxy.ps1`。将修复直接写回该文件无法保持。

最终在 SSH 的 Git Bash 会话中包装按名称调用的 `powershell.exe`：只有编码脚本同时包含专用就绪标记与准确的 helper 导入语句，才把导入引用替换到用户自己的兼容目录。UTF-16 解码、替换和重新编码由独立 PowerShell 脚本完成，其他命令原样传递。

没有使用只读文件、ACL 阻止覆盖、循环写入或监控守护程序。普通 PowerShell 编码命令回归检查也通过。

## 7. 最终验证与清理

- 使用当时捕获的完整 Windows 启动命令，SSH、就绪标记、WebSocket、初始化、账号状态、模型列表全部通过，约 3 秒完成。
- 实际客户端之后用正确用户名认证成功，其运行中的 PowerShell 脚本已引用修复 helper，并有保持连接的 SSH 会话。
- 对父进程链及创建时间核查后，清理了 43 个已断开 SSH 而遗留的旧 proxy 进程及相关外壳。保留仍有 sshd 父链的会话和主后台服务。
- 未获得 app 界面打开项目并成功发送消息的独立确认。协议证据和用户界面验收分别记录。

## 可复用的排查顺序

1. 确認连接方向和真实服务端账户，先解决 SSH 认证。
2. 比较普通 shell、登录 shell、后台运行时的版本与路径。
3. 确认 socket 对应活跃服务、服务权限与启动生命周期正确。
4. 直接测试 proxy，再测试实际客户端使用的 bootstrap。
5. 读取就绪标记后再发送协议字节，验证多个后续请求。
6. 观察客户端是否重写修复文件，检查重连后的实际生效入口。
7. 最后在 app 中完成项目和消息验收。

## 公开版本与现场脚本的差异

仓库脚本从现场实现提取，增加动态目录定位、路径引用、限定 `.exe`、状态检查超时、客户端断开后的代理退出、自动回归测试与脱敏输出。原始客户端启动脚本没有发布；协议探针使用最小合成 bootstrap。

这份仓库是排查记录及特定旧路径的兼容工具，不是当前客户端缺陷已普遍存在、也不是所有 Windows SSH 连接都需要补丁的声明。
